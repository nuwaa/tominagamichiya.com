# Codex Cloudでのサイト更新手順

## 現在の構成

GitHub `nuwaa/tominagamichiya.com`の`main`が原本。本番はCloudflare Pagesで公開し、CMSやGitHub Pagesは使用しない。

| 項目 | 本番設定（本人確認済み） |
| --- | --- |
| 本番ブランチ・自動デプロイ | `main`・有効 |
| ビルドコマンド・出力先 | `npm run build`・`public` |
| HUGO_VERSION | `0.152.2` |
| NODE_VERSION | `18` |
| ビルドシステム | v3 |

Node 22は移行検証先で、本番設定は変更していない。[保守計画](maintenance-plan.md)も参照。

## 初回準備

1. Codex CloudでGitHubを接続し、このリポジトリへのアクセスを許可する。権限は必要なリポジトリに限定する。
2. リポジトリ用のクラウド環境にHugo extended 0.152.2、Node 22とnpmを導入する。本番との比較用にNode 18も使用する。GitHub、Hugo配布元、npmレジストリへの通信を許可し、ルートで`npm ci --include=dev`を実行できるようにする。
3. Codexに`AGENTS.md`を読むよう依頼する。環境や依存キャッシュの復元後も`hugo version`と`node --version`を確認する。
4. GitHubの二要素認証・パスキーと復旧手段を用意する。トークンを原稿やチャット、リポジトリに貼り付けない。

これは準備手順。このPRはアカウント連携やCodex環境設定を自動変更しない。

## ノートPC・ゲーミングPC・iPad

どの端末でも同じアカウントでCodex Cloudを開き、対象リポジトリとタスクを選ぶ。ビルドはクラウド側で行うため、各端末へのHugo・Node・Gitの導入は不要。iPadもブラウザから依頼、GitHubのPR差分確認、Cloudflareプレビュー閲覧まで行える。

進行中の原稿は同じタスクで修正を依頼する。別タスクを作る場合は対象PR・作業ブランチを明示する。未コミットの編集がタスク間で自動共有されるとは考えず、GitHubのブランチ・PRを引き継ぎの基準にする。同じ記事を複数タスクで同時編集しない。

ローカル編集を併用するPCでは、未保存の作業を確認してから最新`main`を取得し、作業ブランチを作る。既存PRの修正はそのブランチを使う。競合は最新`main`を取り込んで解消し、差分を再確認する。force pushや端末間のリポジトリフォルダ同期は使わない。

## 記事・固定ページの依頼

依頼例：

> AGENTS.mdに従って○○の記事を作成してください。対象は一般の生活者、約○字、カテゴリは○○。次の資料を出典にし、事実と見通しを分けてください。新規作業ブランチで編集し、ビルド検証後にPRを作成してください。mainへのマージ・本番公開はしないでください。

記事は`content/articles/<slug>/index.md`に作る。`hugo new content articles/<slug>/index.md`でひな型を作る場合も、生成後にタイトル・カテゴリ・日時を確認する。

```yaml
---
title: "記事タイトル"
date: 2026-10-23T18:00:00+09:00
draft: true
description: "記事の要点"
categories: ["しくみから学ぶデジタル社会"]
tags: ["AI"]
---
```

固定ページは対象ページと変更箇所を指定する。プロフィールや連絡先は本人が示した情報だけを使う。

## 確認・承認・公開

1. Codexが作業ブランチで編集し、`npm ci --include=dev`、`npm run build`、差分チェック後にPRを作る。
2. 本人が「Files changed」で本文・出典・日時・カテゴリと、無関係な変更がないことを確認する。
3. 「Checks」の`Build (Node 18)`と`Build (Node 22)`の成功を確認する。失敗時はマージせず修正を依頼する。
4. 必要なら下記のCloudflareプレビューを確認する。
5. 公開対象が`draft: false`で、日時が未来でないことを確認する。修正が加わったら最新コミットの内容と検証を確認し直す。
6. 本人がPRをマージすると`main`が更新され、Cloudflareが本番を自動公開する。PR作成だけ・Approveレビューだけでは公開しない。自分が作成者のPRには自分でApproveできないため、個人運用では本人のマージを公開承認とする。
7. Cloudflareの本番デプロイ成功と本番URLを確認する。CIの成功だけでは本番デプロイの成功は確定しない。

「PRまで」の依頼では手順6へ進まない。将来Codexにマージを依頼する場合は、対象PR番号と最新内容を指定して明示的に承認する。

このリポジトリは公開されている。`draft: true`はサイトへの出力を抑えるだけで、GitHub上の原稿を非公開にはしない。

## Cloudflare PagesのPRプレビュー確認

以下は確認手順。このPRではダッシュボードを変更しない。項目名は画面更新で変わる場合がある。

1. 対象PagesプロジェクトのGit連携先がこのリポジトリ、本番ブランチが`main`であることを確認する。
2. ビルド・デプロイ設定のプレビューブランチ制御で、作業ブランチ（例：`codex/*`）が対象か確認する。無効・除外の場合は対象ブランチを許可する案と理由を本人に報告する。
3. Preview環境のHugo・Node、ビルドコマンド、出力先を確認する。本番とPreviewの環境変数は別に確認する。Node 22の検証は本人の承認後にPreviewだけを22にする。
4. 作業ブランチのpush／PR作成後、GitHubのCloudflareチェックまたはCloudflareのDeployments一覧を開く。ブランチとコミットSHAがPR最新版に一致し、環境がPreviewであることを確認する。
5. 表示されたプレビューURL（通常`*.pages.dev`）を開く。URLを推測しない。記事にはそのURLの`/articles/<slug>/`から移動し、本文、文字化け、改行、リンクなどを確認する。
6. 修正後は最新コミットのデプロイ成功を待って再確認する。GitHubにCloudflareチェックが出ない場合も、先にDeployments一覧とGit連携・ブランチ制御を調べる。

通常の`npm run build`は下書きを出力しない。`draft: true`の記事はプレビューでも404になる。表示確認には、作業ブランチで公開候補を`draft: false`にし、現在以前の日時で再ビルドする。この変更はマージすると公開対象になるのでPRに明記する。確認の都合で予定日時を変える場合は本人に確認し、承認前に最終日時へ戻す。下書きのまま表示するにはローカル／クラウド内の`npm run dev`を使う。今回プレビュー用ビルドコマンドは変えない。

canonical・OGP・絶対URLは本番ドメインを向く場合がある。リンク移動後のドメインを確認し、本番をプレビューと取り違えない。プレビューURLは秘密情報の保管場所ではない。

## 予約投稿・トラブル対応

- 未来の`date`・`publishDate`だけでは、時刻到来時にビルドは発生しない。予約公開は別途設計する。当面は公開時刻以降に承認・マージする。
- PRビルド失敗時はマージせず、Node版とログをCodexに伝える。
- 本番ビルド失敗時はCloudflareのログと本番URLを確認する。通常は直前の成功デプロイが配信され続ける。
- 公開後の訂正や差し戻しは修正／revert用PRで確認する。緊急のCloudflareロールバックは、対象を確認し本人が承認した場合だけ実施する。
