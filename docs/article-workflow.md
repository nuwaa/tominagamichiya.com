# 一般向け・技術者向けの記事作成手順

最初に[編集ガイドライン](editorial-guidelines.md)と[AGENTS.md](../AGENTS.md)を読みます。ノートPC・ゲーミングPC・iPadのいずれからでも、Codex Cloudで同じPRを確認する運用です。端末設定や既存の公開承認の流れは[運用手順](operations.md)を参照してください。

## 1. 記事を設計する

Codexへの依頼では、テーマと出典を渡し、ガイドラインの「執筆前に整理する7項目」を先に提示させます。一般向け・技術者向けは独立した記事として設計します。必要な片方だけでも構いません。

依頼例：

> このテーマについて、編集ガイドラインに従い一般向けの記事を作成してください。まず読者の疑問・影響・判断・行動・根拠・技術者向け記事の必要性を整理してください。未確認事項は列挙し、創作しないでください。作業ブランチで下書きを作成し、今回はPRまで。マージ・本番公開はしないでください。

## 2. 最新mainから作業ブランチで下書きを作る

Hugo Extended 0.152.2を使い、リポジトリ直下で実行します。既存のslugや初回公開日は変えません。

```sh
hugo new content --kind general articles/example-general/index.md
hugo new content --kind technical articles/example-technical/index.md
```

必要な記事のコマンドだけ実行します。テンプレートは`archetypes/general.md`と`archetypes/technical.md`です。日時はタイムゾーンを確認し、`+09:00`付きの実際の公開予定日時にします。以下は説明用のサンプルです。架空記事を公開用コンテンツとして追加しないでください。

一般向け：

```yaml
---
title: "読者の身近な疑問を起点にしたタイトル"
date: 2026-10-23T12:00:00+09:00
draft: true
description: "読者にとっての影響と、理解・判断できること"
categories: ["しくみから学ぶデジタル社会"]
tags: ["情報リテラシー"]
audiences: ["general"]
companion: "/articles/example-technical"
---
```

技術者向け：

```yaml
---
title: "対象と技術的な論点がわかるタイトル"
date: 2026-10-23T12:00:00+09:00
draft: true
description: "技術的な条件、対応と検証の概要"
categories: ["しくみから学ぶデジタル社会"]
tags: ["情報リテラシー"]
audiences: ["technical"]
companion: "/articles/example-general"
---
```

- `audiences`は配列で`general`か`technical`のどちらか1つです。サイトには「一般向け」「技術者向け」と表示します。既存の未分類記事は項目なしのまま維持します。一律に追加しません。
- `companion`は任意です。不要なら省略または空文字にします。URLではなく、`/articles/<slug>`というHugoのコンテンツパスを指定します。出力URLはHugoが解決するため、既存の記事URLを変更しません。
- 公開済みの対応記事同士は、異なる読者分類を持ち、互いを指定してください。自己参照・同じ分類・参照先の未分類・片方向だけの参照は、両方が公開対象になったビルドでエラーになります。
- 対応先が存在しない、下書き、未来の`date`／`publishDate`、期限切れ、HTML出力なしの場合はリンクを表示しません。これは公開準備中を許容する仕様です。非表示の場合もパスの誤記でないか手動確認してください。
- 正しい組には本文の前後に日本語の案内が出ます。片方だけ先に公開してもリンク切れを出さず、後日もう片方が公開対象になったビルドで案内が出ます。

## 3. 原稿と表示をレビューする

一般向け・技術者向けそれぞれのレビューチェックリストを使い、対応記事間の事実認識も照合します。既存原稿の改稿はURL・初回公開日・出典を維持し、実質的な変更時に`lastmod`を更新します。

```sh
npm ci --include=dev
npm run build
python3 scripts/test_editorial.py
git diff --check
```

Python 3の標準ライブラリのみでテストします。テスト用記事は一時ディレクトリに生成・削除し、`content/`や本番出力には追加しません。Node 18／22のPR CIで同じ検証を行います。

- 通常の`npm run build`は下書き・未来日付・期限切れを除き、Pagefindも公開出力を索引化します。
- ローカルで下書きを読む場合は`npm run dev`（`-D`）を使います。下書きである対応記事への案内は、この場合も表示しません。
- Cloudflare PRプレビューは本番と同じ条件のため、`draft: true`は表示されません。公開候補の表示確認が必要なら、本人に示したうえで`draft: false`に変更し、PRに「マージすると公開対象」と明記します。秘密原稿は公開GitHubに置けません。
- 未来日付は時刻到来だけでは公開されず、次のビルドが必要です。下書き・未来日付を表示するオプションを本番ビルドに追加しません。
- 記事一覧の「すべての記事」「一般向け」「技術者向け」、各記事の分類、対応記事の冒頭・末尾リンクをPCとスマートフォンで確認します。分類未設定の記事も引き続き「すべての記事」で読めます。

## 4. PR確認と公開承認

PRには7項目の設計、内容と出典、変更範囲、公開対象か、検証結果、Cloudflareプレビュー、未確認事項を書きます。本人が内容とプレビューを確認し、対象PRの最新内容について明示的に公開を承認してからマージします。「PR作成まで」の依頼ではマージも自動マージも行いません。mainへの更新がCloudflareの本番公開を起動します。
