# 一般向けの記事作成手順

最初に[AGENTS.md](../AGENTS.md)、[EDITORIAL_GUIDE.md](../EDITORIAL_GUIDE.md)、[ARTICLE_TEMPLATES.md](../ARTICLE_TEMPLATES.md)、[FACT_CHECK_POLICY.md](../FACT_CHECK_POLICY.md)を読みます。記事は、ITの専門知識がない女子中学生にも読める文体の、一般向けの簡潔な解説に統一します。技術者向けの別記事や二段階の記事セットは制作しません。

ノートPC・ゲーミングPC・iPadからのCodex Cloudの利用方法は[運用手順](operations.md)を参照してください。

## 1. 記事を設計する

テーマと出典を渡し、EDITORIAL_GUIDE.mdの「執筆前に整理すること」を整理します。事件・障害、用語解説などの記事の種類と中心の視点を決め、過去の流れを継承するひな形を使います。

依頼例：

> 編集ルールに従って、一般向けの簡潔な解説を作成してください。文体はITの専門知識がない女子中学生にも読めるものにしてください。まず記事の種類・中心の視点・読者の疑問・影響・判断・行動・根拠を整理し、従来の解説に沿って書いてください。未確認事項は列挙し、創作しないでください。技術者向けの別記事は不要です。今回は下書きとPRまで。マージ・本番公開はしないでください。

同じ事案を企業・教育など別の視点から書く場合も、文体は一般向けで統一します。別の記事を読まなくても、それぞれで理解・判断できるようにします。

## 2. 最新mainから作業ブランチで下書きを作る

Hugo Extended 0.152.2を使い、リポジトリ直下で実行します。

```sh
hugo new content --kind general articles/example-general/index.md
```

使うarchetypeは`archetypes/general.md`です。次はFront Matterの記入例です。日時・タイトル・説明・カテゴリー・タグを実際の原稿に合わせて置き換えます。日時は日本時間（`+09:00`）を確認します。

```yaml
---
title: "読者の疑問と記事の視点が伝わるタイトル"
date: 2026-10-23T12:00:00+09:00
draft: true
description: "読者にとっての影響と、理解・判断できること"
categories: ["しくみから学ぶデジタル社会"]
tags: ["情報リテラシー"]
audiences: ["general"]
companion: ""
---
```

- 新規記事の`audiences`は`["general"]`です。既存の未分類記事を一律に分類しません。
- `companion`は省略または空文字にします。新しい相互参照セットは作りません。別視点の関連記事は、公開状態を確認して通常の本文リンクで紹介します。
- 過去に追加した`technical`の分類、archetype、対応記事リンク機能は互換性のため残っていますが、現在の制作には使いません。機能の削除やメニュー変更は、この文書整備とは別の作業です。
- 既存のslugと初回公開日は変更しません。改稿では実質的な更新時に`lastmod`を設定します。取り下げ済みの記事は明示的な再公開依頼なしに公開へ戻しません。

## 3. 内容と表示を確認する

EDITORIAL_GUIDE.mdのレビューとFACT_CHECK_POLICY.mdの確認表を使います。「女子中学生にも読めるか」「短く整理されているか」「原因・問題点・立場別の対策がわかるか」「重要な条件を省いていないか」を確認します。同じ事案の記事がある場合は事実認識を照合します。

```sh
npm ci --include=dev
npm run build
python3 scripts/test_editorial.py
python3 scripts/test_tables.py
python3 scripts/test_emphasis.py
git diff --check
```

- 本番ビルドは下書き・未来日付・期限切れを除き、Pagefindも公開出力を索引化します。CIではNode 18／22を検証します。
- 下書きのローカル表示は`npm run dev`（`-D`）を使います。Cloudflare PRプレビューは本番と同じ条件なので、`draft: true`は表示されません。
- 公開候補の表示確認が必要なら、本人に示したうえで`draft: false`へ変更し、PRに「マージすると公開対象」と明記します。秘密原稿は公開GitHubに置きません。
- 未来日時は時刻到来だけでは公開されず、次のビルドが必要です。下書き・未来日付を出力するオプションを本番ビルドに追加しません。
- 見出し、段落、箇条書き、太字、表、リンクをPCとスマートフォンで確認します。サンプル記事は公開コンテンツに残しません。

## 4. PRと公開承認

PRには執筆前の設計、内容と出典、変更範囲、公開対象か、検証結果、プレビュー、未確認事項を書きます。記事内容の確認と公開承認は区別します。本人が対象PRの最新内容を明示的に承認してからマージします。「PR作成まで」の依頼ではマージ・自動マージを行いません。mainの更新はCloudflareの本番公開を起動します。
