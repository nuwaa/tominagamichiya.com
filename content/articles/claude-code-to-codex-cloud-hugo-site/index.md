以前、Claude Codeに相談しながら、個人サイトをWordPressから静的サイトへ移行しました。

Hugoでページを生成し、記事はMarkdownで管理する。GitHubに変更を送れば公開できる――そんな仕組みを作ったはずでした。

ところが、久しぶりに更新しようとしたら、**どうやって投稿するのか、すっかり忘れていました。**

「脱WordPress」はできても、肝心のサイト運用が続いていなかったのです。

そこで今回は、以前のClaude Codeとは別のAIであるCodex Cloudに、既存のGitHubリポジトリを調べてもらうところから始めました。

## AIが作ったものを、人間が引き継げない

生成AIと一緒にコードを書くと、短時間で動くものを作れます。これは大きな利点です。

ただし、**完成したコードと、継続して運用できる仕組みは別物**です。

サイト自体が動いていても、更新の手順、公開先、必要なバージョン、失敗したときの戻し方を忘れてしまえば、再開するたびに調査が必要になります。

今回の問題は、Hugoを選んだことそのものではありません。運用方法を将来の自分が読める形で十分残していなかったことです。

## まず、Codexには変更させず調査させた

リポジトリは [nuwaa/tominagamichiya.com](https://github.com/nuwaa/tominagamichiya.com) です。

Codex Cloudには、最初に「構成と公開経路を調査するだけ。ファイル変更や本番公開はしない」と指示しました。

調査で確認した主な構成は、次のとおりです。

| 役割 | 採用していたもの |
| --- | --- |
| 静的サイト生成 | Hugo |
| 記事原稿 | Markdown |
| ソース管理 | GitHub |
| サイト内検索の索引生成 | Pagefind |
| 公開先 | Cloudflare Pages |
| ビルド | `npm run build` |
| 公開の基点 | GitHubの `main` ブランチ |

ここで意外だったのは、リポジトリ内に**古いGitHub Pages向けの定期デプロイ処理**が残っていたことでした。

READMEにはCloudflare Pagesの記述があり、GitHub Actionsには別の公開先に生成物を送る処理がある。これでは、どちらが本番の仕組みなのか判断しにくくなります。

Cloudflareの管理画面を確認した結果、本番ではGitHubの`main`を監視し、Hugoをビルドして公開する設定が有効だとわかりました。

**コードだけを読んで推測するのではなく、実際の設定を確認する。** この手順を踏んだことで、不要な作り直しを避けられました。

## GitHubを「共通の原本」にした

もう一つの希望は、ノートPCだけでなく、ゲーミングPCやiPadからも更新できるようにすることでした。

特定のパソコンにしか最新原稿がない仕組みでは、また同じ問題が起こります。

そこで、GitHubの`main`を正式な原本とし、Codex Cloudが作業ブランチで変更し、Pull Request（PR）で確認してから公開する方式にしました。

流れは、こうです。

1. どの端末からでもCodex Cloudに作業を依頼する。
2. Codexが作業ブランチで原稿やコードを変更する。
3. GitHub Actionsがビルドを検証する。
4. Cloudflare Pagesのプレビューで画面を確認する。
5. **本人がPRをマージしたときに限り、`main`の更新を本番へ反映する。**

AIが作業を助けても、公開の判断は人間が行います。

自分が更新手順を忘れたときのために、`AGENTS.md` と日本語の運用手順書も残しました。

## 小さなPRに分けた理由

今回の作業は、いきなりサイト全体を作り直すのではなく、三つのPRに分けました。

### PR #1：運用の整備

[PR #1](https://github.com/nuwaa/tominagamichiya.com/pull/1)では、古い定期デプロイ処理を整理し、PRごとのビルド確認と、Codexが守る編集・公開ルールを整備しました。

Node.js 18と22の双方でビルドする検証も追加しました。ただし、**本番のNode.jsを22へ移行する作業は、この時点では行っていません。**

### PR #2：プロフィールの再整備

[PR #2](https://github.com/nuwaa/tominagamichiya.com/pull/2)では、自己紹介、About、Media Kitを更新しました。実績の出典や連絡先、本人写真も整えています。

ここではちょっとした問題がありました。

Codexが外部サイトから本人写真を取得しようとしても、クラウド環境のネットワークプロキシに遮断され、取得できなかったのです。

画像配信元がエラーを返したわけではなく、接続要求の段階で拒否されていました。

結局、私が写真をGitHubの作業ブランチにアップロードし、Codexにはそのファイルを配置してもらう方法で解決しました。

**AIがうまくできないところは、人間が別の経路を用意する。** これも現実の運用です。

### PR #3：デザインの改善

[PR #3](https://github.com/nuwaa/tominagamichiya.com/pull/3)では、本人写真、実績、専門分野を読みやすく見せるよう、HugoのテンプレートとCSSを整理しました。

ブラウザ幅ごとの表示を検証し、記事本文や公開URLを維持したままデザインを改善しました。

毎回、差分とプレビューを確認してからマージしています。実際にマージ後、独自ドメインへの表示を確認するまでには少し時間差もありました。**GitHubのマージ成功と、閲覧者から見える本番反映の確認は別の作業**だと実感しました。

## 「脱WordPress」が目的ではない

今回の構成を、すべてのWebサイトにおすすめするつもりはありません。

静的サイトには、更新する仕組みが単純で、公開側にWordPressの管理画面やプラグイン群を置かなくて済むという利点があります。一方、記事を書く人が複数いる場合や、管理画面での更新を重視する場合には、CMSのほうが適していることもあります。

また、静的サイトでも、GitHubの権限管理、依存パッケージ、ビルド環境、外部サービスへの接続は管理しなければなりません。

「WordPressだから危険」「静的サイトなら安全」という二択ではないのです。

大切なのは、そのサイトを**誰が、どれくらいの頻度で、どんな体制で運用するのか**という条件から、必要な仕組みを選ぶことだと思います。

## AIに任せるなら、引き継ぎまで設計する

今回、最も大きな収穫は、サイトが更新できるようになったことだけではありません。

以前のAIと作った仕組みを、別のAIが読み解き、改修できるようにしたことです。

そのためには、コードだけでなく、運用上の約束事が必要です。

- 正しい情報の置き場所を一つにする。
- 変更を小さく分け、履歴を残す。
- 動作確認と本番公開を分ける。
- 実際の設定とドキュメントを一致させる。
- 人間が承認する箇所を明確にする。

これらは生成AIだけの話ではありません。人が担当するシステムでも、同じように必要なことです。

## これから

今回の再整備で、ようやく「更新方法を忘れたサイト」から「更新を続けられるサイト」へ戻す土台ができました。

検索画面やOGPなど、引き続き改善したい箇所はあります。本番のNode.jsの移行も別の課題です。すべてが完成したというわけではありません。

それでも、今度はサイトを作ること自体に時間を使いすぎず、記事を書き、技術と社会の問題を説明する場所として運用していきたいと思います。

AIを使って何かを作ることは、以前より簡単になりました。

**では、その成果を、誰がどう使い、誰が責任を持って維持するのか。**

そこまで考えることが、私の考えるテクノロジストの仕事なのだと思います。
